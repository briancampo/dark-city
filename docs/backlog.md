## 1. How to Use This Backlog

This backlog is the Steward's source of truth for dispatching work. A few conventions, so it converts cleanly into GitHub issues:

- **One story = one GitHub issue.** Epics are for grouping and sequencing only — the Steward tracks epic-level progress, but never dispatches an epic as a single unit of work.
- **ID scheme:** `Phase.Epic.Story` — e.g., `1.2.3` is Phase 1, Epic 2, Story 3. Use the ID as the GitHub issue's reference tag in its title (e.g., `[1.2.3] Cognitive Controller module`).
- **Estimates** are relative complexity points (1, 2, 3, 5, 8, 13), not hours — used for sequencing and load-balancing across roles, not for schedule commitments.
- **Depends On** lists prerequisite story IDs. The Steward should not dispatch a story until everything it depends on has merged — this is what keeps Session Start Workflow's "check the codebase is green" step meaningful.
- **Blueprint §** is the exact World Blueprint section the assigned agent should read per Session Start Workflow step 3. Every story traces to one; if a story doesn't cleanly map to an existing section, that's a signal the Blueprint needs an amendment before the story is dispatched, not a reason to proceed without one.
- **Owner** is a single Dark Factory role, per Team Charter §3.1. A story that seems to need two roles should be split into two stories, not force-assigned.
- Each phase closes with **Exit Criteria** — the concrete bar for calling a phase's runnable product done and moving to the next, per Design Foundations' principle that every phase ships something we actually run and learn from.

### Phase 1 Exit Criteria

- All Epic 1.0–1.6 stories merged and passing CI.
- The Phase 1 scenario runs continuously for a sustained simulated period **with no viewer client attached at all**, without crashing or requiring manual intervention — the concrete proof that the backend is genuinely headless and authoritative (Decision 0002).
- The 1.6.2 findings write-up exists and explicitly addresses whether citizen behavior reads as coherent (Controller bottleneck working as intended) and whether the async inference offload bridge (1.2.7) holds the tick schedule steady under real inference load.
- A second, throwaway world instance has been created and torn down via the World Session Manager (1.1.6) alongside the primary Phase 1 world, confirming isolation holds even though Phase 1 only exercises one world in earnest (Decision 0003).
- Any parameter found to need adjustment (reflection threshold, recency decay, tool catalog size) has a decision log entry recording the change.

## 7. Backlog Maintenance

This backlog will grow as phases complete and real runs surface gaps the Blueprint didn't anticipate. New stories follow the same `Phase.Epic.Story` scheme, extending existing epics (e.g., a new `2.6.x` epic) rather than renumbering anything already in flight. Any story that reveals a genuine gap in the World Blueprint should trigger a decision log entry — and, if the gap is significant, a Blueprint amendment — before implementation gets far ahead of the spec it's supposed to be implementing. The Steward owns keeping this backlog's status current; individual developer agents update their assigned story's status as part of the PR they open against it, per Session Start Workflow step 10.
