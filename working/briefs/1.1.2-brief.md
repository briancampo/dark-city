The viewer client (`dark_city_client`) is a thin, stateless renderer — it holds no `CitizenState` and makes no simulation decisions.

Nothing about the network layer may assume there is exactly one world — every connection names the one `world_id` it cares about.

## 2. Dispatched Scope & Acceptance Criteria

### Ticket [1.1.2] Axum Server Skeleton + Per-World WebSocket

- **Role:** System Architect
- **Directory Ownership:** `crates/dark_city_server/`
- **Blueprint Reference:** [§2 (System Architecture Overview)](../../docs/dark-city-blueprint.md#2-system-architecture-overview), [§3.4 (Viewer Client & State Broadcast)](../../docs/dark-city-blueprint.md#34-viewer-client--state-broadcast), [§12 (Networking & API Surface)](../../docs/dark-city-blueprint.md#12-networking--api-surface)
- **Goal:** As a System Architect, I want a running Axum server with a `/ws/world/:world_id` handler so that state broadcasts have a per-world channel to travel over.

- **Acceptance Criteria (per `docs/backlog.md`, Epic 1.1, revised row):**
  - Given the server is running and a world exists, when a client connects to `/ws/world/:world_id`, then it receives a connection-ack message **and a full state snapshot scoped to that world only** — no data from any other `world_id` is ever present on the connection.
  - Given a client connects with a `world_id` that does not exist in the `worlds` table, then the connection is rejected (closed with an explicit error code/reason) rather than silently returning an empty or default snapshot.
  - Given two clients connect to two different `world_id`s concurrently, then each receives only its own world's snapshot — no cross-world leakage, by construction (separate query scoping, not application-level filtering after the fact).

- **Implementation notes (read before starting):**
  - **This ticket is a skeleton, not the full broadcast pipeline.** At this stage, no PIANO modules (Epic 1.2) or `CitizenState` ECS components (1.1.5, 1.2.1) necessarily exist yet, so the "full state snapshot" this ticket returns may legitimately be sparse — whatever the `worlds` row and any already-migrated tables (`citizens`, if seeded) actually contain. The acceptance criteria are about the **shape and scoping** of the response, not its richness. Later tickets (1.5.2 world initialization, 1.2.x modules) are what make the snapshot substantive.
  - **Testing without 1.1.6.** Because the World Session Manager (1.1.6) may not have merged yet, you will likely need a test fixture that inserts a `worlds` row directly via the 1.1.1 migrations (not through `POST /api/v1/worlds`) to have a `world_id` to connect against. Don't block this ticket on 1.1.6 — just be explicit in your tests about which path (fixture insert vs. real API) you're using, and note it in the test with a TODO(1.1.6) and your PR/handoff so a later ticket can revisit test setup once 1.1.6 exists.
  - **Resync semantics (Blueprint §3.4).** The "on connect, full snapshot first" behavior isn't a one-time bootstrap detail — Blueprint §3.4 point 2 requires the _same_ behavior on every reconnect after a drop, so any viewer client (present or future, and any number of them per Decision 0002) never renders from a stale partial-delta baseline. Implement the snapshot path so it's naturally reusable on reconnect, not as a connect-only special case.
    - Determine what a state sync snapshot must contain and ensure that it is updated as we go forward with other tickets.
  - **Out of scope for this ticket:** actual per-tick state delta broadcasting (movement, `current_action`, dialogue, Narrator editions, proximity flags) — that traffic depends on modules that don't exist yet (Epic 1.2 onward) and is not required to close this ticket. This ticket's job is the connection lifecycle and the initial snapshot contract; wiring live deltas into the same channel is implicitly covered by later tickets as those systems come online, not a gap to fill here.
