# [0006] Mandatory Review Gate for Citizen-Authored Tools

**Date:** 2026-08-30
**Ticket:** Pre-Epic-3.1 architecture correction (raised ahead of Phase 3 dispatch, per review against Emergence World's tool-authoring pipeline)
**Role:** Steward (facilitated), for Tech Lead ratification before start of Phase 3

## Question

Once citizens can author and register their own tools (Blueprint §5.3, Backlog Epic 3.1), should anything stand between a passed `new_tool` governance proposal (§6) and that tool actually entering the live `ToolDefinition` registry — given that a registered tool's effect handler executes as ordinary logic inside `dark_city_server`, with the same trust level as any other platform code, not inside a sandbox?

## Options Considered

1. **No gate (status quo).** Backlog 3.1.1 → 3.1.2 currently goes straight from a passed proposal to runtime registration. The 70% supermajority vote is the only checkpoint.
2. **Automated static analysis only.** A compile/lint pass (and, if feasible, a sandboxed trial execution) checking the submitted code builds cleanly and doesn't do anything trivially detectable as unsafe (unbounded loops, disallowed syscalls/imports, etc.).
3. **A dedicated, non-autonomous Tool Review Agent persona**, modeled on Emergence World's mandatory `Code Review Agent` (Appendix C of that paper): an invisible system persona — not a citizen, never plans or acts on its own initiative — that receives the submitted tool code and schema, and returns a grammar-enforced, structured verdict (`approve` / `reject` + findings) before registration is allowed to proceed.
4. **Human (Steward) manual review of every citizen-authored tool before registration.**

## Decision

**Option 3, informed by Option 2 as a cheap first-pass filter, not a replacement for it.** A submitted tool's code first passes a static/compile check (catches malformed or trivially unsafe code cheaply); what survives is then reviewed by a new **Tool Review Agent** — authored and invoked the same way the Narrator is (§8.1): non-autonomous, invisible to the citizen roster and to governance/tool systems, activated only when triggered (here, by a passed `new_tool` proposal with attached code), and constrained to a grammar-enforced structured output the same way tool-call JSON already is (§5.2). Only an `approve` verdict allows the existing passage handler (§6) to proceed to `ToolDefinition` runtime registration; a `reject` verdict blocks registration, and its findings are surfaced back to the proposing citizen through ordinary in-world channels (a system message, comparable to how proposal rejection is already communicated).

## Why

- **Tool code is a different risk category than anything else a citizen produces.** A citizen's dialogue, diary entry, or proposal text all stay data — read by other modules, never executed. A registered tool's effect handler is the one path by which citizen-generated content becomes code the runtime executes with full platform trust. Design Foundations §8's defense-in-depth stack (model / environment / population / instrumentation) implicitly assumes every `ToolDefinition` already in the registry is trustworthy; nothing in that stack currently guards the moment a _new_ one is admitted. This decision closes that specific gap — it extends the Environment layer to cover admission-time (is this tool safe to add), where `validate_tool_access` (§5.2) already covers call-time (is this call to an already-trusted tool currently permitted).
- **Emergence World treats this as non-negotiable, and for good reason.** That platform's tool-creation pipeline (Appendix B/C of that paper) makes Tool Review Agent approval mandatory — "no tool enters the global registry without it" — specifically because it's the one point where model-generated content crosses from text into executable logic. Dark City's citizen-authored tools cross exactly the same line, in a backend with no sandbox around tool execution (Blueprint §5.2 already establishes the Rust runtime, not the model, as the sole enforcement point for tool access — that guarantee is only as good as what's in the registry to begin with).
- **A 70% vote is a social-consensus signal, not a security review, and shouldn't be treated as one.** Both Emergence World and Project Sid show populations passing proposals that later prove harmful, exploitable, or simply not what the population thought it was voting for (Emergence World's own soft-violation, vote-buying, and misinformation findings, §5–6 of that paper, are evidence that a citizen population's collective judgment about a proposal's _content_ and its judgment about the proposal's _tool_ are not the same evaluation). Option 1 is rejected on this basis.
- **Static analysis alone (Option 2) catches the wrong failure mode.** It can confirm code compiles and avoids obviously disallowed constructs, but it cannot catch a tool whose effect handler is syntactically unremarkable yet semantically harmful — e.g., a "gift" tool that quietly transfers more credits than its description claims. That's a judgment call about _intent and effect_, which an LLM-driven review persona is suited to and a static pass is not. Option 2 is retained as a cheap pre-filter feeding into Option 3, not as a standalone answer.
- **Human/Steward review (Option 4) is rejected on the same grounds Design Foundations §7 gives for decentralized governance generally** — it doesn't scale past a handful of tools and reintroduces a bottleneck the platform is explicitly designed not to have — **and on a second, more specific ground**: Design Foundations §2 draws a hard boundary that Dark Factory "has no presence inside the simulated world, ever." A Steward-in-the-loop gate on in-world tool content would be exactly the kind of boundary violation that section warns against, however well-intentioned. A system-level, invisible persona (Option 3) keeps the review _inside_ Dark City, consistent with how the Narrator already handles the one other case of "non-citizen judgment applied to in-world content."
- **Modeling it as a persona rather than a bespoke function keeps the pattern consistent.** The Narrator (§8.1) already establishes the shape for "authored like a citizen, but non-autonomous and invisible to governance/tools." The Tool Review Agent reuses that shape rather than inventing a new one, and grammar-enforcing its verdict (§5.2's existing pattern for tool-call JSON) means the passage handler can act on the verdict directly without a second layer of free-text interpretation.

## Impact

- **Design Foundations §8 (Safety Stack):** Environment-layer bullet revised to distinguish call-time gating (`validate_tool_access`, already-registered tools) from admission-time gating (Tool Review Agent, new tools) as two distinct sub-guarantees of the same layer.
- **World Blueprint:** New subsection (§5.4, "Tool Review Gate for Citizen-Authored Tools," following the §5.3 Tool Catalog Growth pattern) describing the Tool Review Agent persona, its trigger condition, its grammar-enforced verdict schema, and its place in the `new_tool` passage handler between proposal passage (§6) and runtime registration (§5.3). §6's `new_tool` passage-handler description gains a one-line cross-reference to §5.4.
- **Team Charter §3.1:** Local Inference Specialist's responsibility line gains "implements the Tool Review Agent persona and its grammar-enforced verdict schema"; System Architect's gains "wires the Tool Review Gate into the `new_tool` passage handler ahead of runtime registration."
- **Backlog:**
  - New story **3.1.4** — "Tool Review Agent: audit gate for citizen-authored tools" (Local Inference Specialist), Depends On 3.1.1.
  - **3.1.2** ("Runtime `ToolDefinition` registration") revised: Depends On gains 3.1.4; acceptance criteria revised so registration is conditional on an `approve` verdict from 3.1.4, and a `reject` verdict is a defined, tested outcome (tool not registered, findings surfaced to the proposing citizen), not just an implicit non-case.
  - **Phase 3 Exit Criteria** bullet ("At least one citizen-authored tool has been proposed, passed, and used in a run") revised to add "...after passing the mandatory tool-review gate (Decision 0006)."
