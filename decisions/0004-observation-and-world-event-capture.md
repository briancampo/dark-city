# [0004] Observation & World-Event Capture

**Date:** 2026-08-29
**Ticket:** Design/research brief — `research-brief-perception-and-world-events.md` (not yet a dispatched backlog ticket)
**Role:** Character Sculptor (Problem A: citizen observation) & System Architect (Problem B: world-event schema and production), facilitated jointly, for Tech Lead ratification

> **Project state note:** at the time of this decision, only Epic 1.0 (repository/tooling bootstrap) and Story 1.1.0 (containerized deployment) are complete. Nothing in Epic 1.1 onward has merged. This is a genuine clean slate — schema and backlog impacts below are written as direct amendments to not-yet-dispatched tickets, not as follow-up migrations against closed work.

## Question

Two related but separate gaps, both surfaced by the same review: **(A)** no PIANO module gives a citizen any way to notice something it didn't do and wasn't spoken to about — another citizen's visible action, a public event nearby, anything ambient; **(B)** even if (A) is fixed, there is no mechanism for a world event that no citizen caused at all — weather, a scripted disaster, a resource-scarcity threshold crossing, a scheduled festival. Should Dark City add a formal ambient-awareness mechanism, and separately, a producer and schema for citizen-less world events? If so, what shape should each take, and in which phase?

## Options Considered

### Problem A — Citizen Observation

1. **New formal Observation module** (fast/reflexive system, reusing the `bevy_spatial` index already built for tool gating and bulletin visibility, §5.1/§8.3). Scans for events/entities within a citizen's spatial awareness radius that the citizen didn't cause (Action Awareness's job) and wasn't a direct party to (Social Awareness's job), filters obvious noise through a cheap event-type salience lookup, and writes qualifying candidates directly to the citizen's episodic memory stream — where the existing importance-scoring prompt (§4.2/§4.3) takes over exactly as it already does for any other observation.
2. **Fold into Memory's existing "writes new observations" responsibility.** No new module; Memory gains an additional *active*, periodic proximity-scan duty on top of its current *passive*-recipient duty.
3. **Generalize Action Awareness and Social Awareness** to also cover ambient/third-party events, split by rough category (world-adjacent vs. social-adjacent), rather than adding a fourth module.

### Problem B — World Events With No Citizen Actor

**Schema:**
1. **Loosen `simulation_events`**: make `citizen_id` nullable, add a `source` discriminator.
2. **Dedicated `world_events` table**, `world_id`-scoped like every other per-run table (Decision 0003), left separate from the citizen-attributed `simulation_events`; an `observable_events` view unions both for read paths (Observation, Narrator) that need "everything nearby," regardless of source.
3. **Staging table** normalized into `simulation_events` after production — an extra pipeline stage with no clear benefit over (1) or (2) directly.

**Producer:**
1. **Scenario-scripted timeline only** — extend the scenario package (§10.1) with an optional, ordered list of timed events; a scheduler system in the per-world headless tick fires them at `sim_clock` crossings.
2. **System-computed threshold-crossing detector only** — a polling system (Narrator-cadence-style) watching a small, named set of aggregates (starting with ledger balance crossing zero, §7) and emitting an event when a threshold crosses.
3. **Citizen-triggered only** — a citizen's own tool-call effect spawns an independent, ongoing world event that outlives or outreaches the acting citizen (e.g., a fire that burns for hours regardless of whether the citizen who started it is still present).
4. **All three**, as independent, narrowly-scoped producers sharing one sink (the schema from above) — not one mechanism trying to do two or three jobs.

## Decision

**Problem A: Option 1, named Observation.** Observation becomes a new PIANO module (Design Foundations §4 module table and Blueprint §3.2 both gain an entry). It runs as a fast/reflexive system on a coarser-than-per-tick cadence (a tunable parameter, per Design Foundations §14's existing pattern for empirically-adjusted constants), queries `bevy_spatial` for what's nearby, filters through a small, config-loaded (not hardcoded) event-type → salience lookup, and writes surviving candidates straight to episodic memory. **It does not pass through the Cognitive Controller** to decide *what* happens — but see the urgency addendum below for *when* the Controller reconsiders.

**Problem A, addendum — urgency and immediate reaction.** Observation's salience filter gates two things, not one: a lower **memory threshold** (is this worth remembering at all) and a higher **urgency threshold** (is this worth interrupting the Controller's normal cadence for). An observation clearing the urgency threshold flags the affected citizen for an immediate, out-of-cadence Cognitive Controller cycle, in addition to being written to memory. This mirrors Smallville's own reaction check, which runs against every newly perceived observation rather than waiting for a scheduled planning pass. Observation still never writes `current_action` or `pending_dialogue` — the Controller still does, and still is the only thing that does — Observation only changes *when* the Controller is invoked for that one citizen, never *what* it decides.

**Problem B, schema: Option 2.** A new `world_events` table, plus an `observable_events` view that unions it with `simulation_events` for any consumer (Observation, Narrator) that needs "everything nearby regardless of who or what caused it." `simulation_events` itself is untouched in shape.

**Problem B, producer: Option 4.** Build all three, each intentionally minimal: a scenario-scripted timeline, a single concrete threshold-crossing case (ledger balance crossing zero), and a citizen-triggered path (a tool's effect handler may, alongside its normal `simulation_events` write, insert a `world_events` row when the effect is meant to persist or ripple beyond the acting citizen).

## Why

**Observation as a new module, not a retrofit of Memory or the two Awareness modules.** Smallville — the paper Design Foundations §3 already credits for Dark City's memory and planning design — has an explicit perceive step: everything within a citizen's visual range is fed into its memory stream every tick, independent of the citizen's own actions or conversations, and Smallville's own vocabulary calls every such entry an "observation" (Design Foundations §5 already uses this exact word to describe episodic memory content). PIANO (Project Sid) doesn't name a Perception module, but that's because it's built on a game engine (Minecraft) that supplies ambient world state through the environment layer rather than a named cognitive module — a pattern that doesn't transfer here, since Dark City's "engine" (the headless ECS) is exactly where PIANO modules already live. Folding this into Memory (Option A2) blurs one module into two very different cadences and responsibilities — passively recording what other modules already hand it, versus actively polling a spatial index — cutting against the "each module reads/writes independently, at its own cadence" concurrency model the rest of PIANO already relies on. Generalizing Action Awareness and Social Awareness (Option A3) is worse: Action Awareness's whole reason for being is comparing a citizen's *own* intended action to what happened, and Social Awareness's is interpreting cues from *direct* interaction — stretching either to cover a third citizen's arson nearby introduces exactly the classification ambiguity a clean module boundary is supposed to prevent.

**Naming it Observation, not Perception.** "Perception" is heavily loaded in game AI generally (sight cones, hearing radius, occlusion — a true sensory subsystem), and this module is a coarser thing: an abstract spatial-radius query, not line-of-sight simulation. Calling it "Observation" ties it to language the project already uses for episodic memory content, avoids overclaiming a sensory fidelity it doesn't have, and leaves "Perception" available for an actual future sensory mechanism (blocked-by-walls sight, hearing distance distinct from sight distance) that would genuinely deserve the name.

**Immediate reaction requires an urgency path, not just a write-and-wait design.** As first drafted, Observation wrote straight to memory and relied on the Controller's normal periodic cadence and Planning's reaction-event mechanism (§4.4) to eventually pick it up. That's the right default for routine ambient noise — most of what a citizen notices shouldn't interrupt anything — but it's the wrong default for a fire in the kitchen. Smallville's reaction check runs per-observation, not on a coarse schedule; Dark City needs the same property for genuinely urgent content without giving up the coarser cadence's compute savings for everything else. An urgency flag that forces an out-of-cadence Controller cycle for just the affected citizen gets both: cheap routine observation, immediate urgent reaction, and no change to who's allowed to write `current_action`/`pending_dialogue`.

**Separate `world_events` table over loosening `simulation_events`.** `simulation_events` is already load-bearing: Backlog 1.6.1 (structured event logging) and every future AWI query built against it assume citizen attribution. A separate table also resolves the brief's original M2 question by construction: M2 (§9.2) measures citizen norm-adherence — a scripted disaster or a threshold crossing isn't a signal about any citizen's behavior, so it should never be eligible for M2, and a citizen-triggered world event's `origin_citizen_id` is provenance only, never an M2 signal either (the *causing* tool call is already separately logged in `simulation_events` and is already M2-eligible there). The `observable_events` view exists purely so Observation and the Narrator have one thing to query instead of two.

**Building all three producers, minimally.** The brief's own evidence shows the scripted and threshold-crossing gaps are real and already-implied, not hypothetical — the Narrator's "resource scarcity events" line (§8.2) has zero producer today, and scenario packages already gesture at "episode seeds." The citizen-triggered path closes a gap the brief didn't originally name but that the same review surfaces once you look at what a tool like Emergence World's `arson_building` actually does: it doesn't just log an instant action, it produces an ongoing state (a building that burns for hours) that other citizens can discover independently of the citizen who caused it — exactly the shape Problem B describes, just sourced from a citizen's own action rather than a scenario or a threshold. None of the three producers is built as a general framework ahead of a second concrete use case — the threshold-crossing producer ships with exactly one case (ledger balance crossing zero), and the citizen-triggered path ships as a documented pattern for tool-effect handlers to opt into, not a generic "any tool can spawn a world event" mechanism, since Phase 1's core-only tool catalog has nothing that would exercise it yet.

**M10 needs no change.** The brief raised, as an open question, whether the soft-violation classifier should ever scan raw observation content directly. On inspection it doesn't need to: Blueprint §9.3 already scopes M10 to "logged speech act, stated plan, and diary entry" — a raw observation carries no citizen intent until the citizen actually speaks about it, plans around it, or writes it into a diary, at which point it's already inside M10's existing scope. This closes the question rather than deferring it; no amendment is needed here.

**Scenario start time, and a simulated-vs-wall-clock fix.** Scripted events need an anchor to be expressed as absolute world-clock times rather than pure elapsed duration since world start — so the scenario package gains a `starting_time` field, seeded into the new world's `sim_clock` at creation (§10.2), and `scripted_events[].trigger_time` becomes an absolute timestamp compared directly against `sim_clock`. Working through this surfaced a related bug worth fixing in the same pass: `world_events.occurred_at` should represent *simulated* time (the world's own clock), not wall-clock insertion time — a headless simulation's tick rate isn't guaranteed to track real time 1:1, so `DEFAULT now()` would silently conflate the two. `occurred_at` is populated explicitly from `sim_clock` at production time; a separate `created_at` (real wall-clock) is kept for ops/debugging only.

**Phasing.** Observation (Problem A) belongs in **Phase 1** — cheap (reuses existing infra, no LLM call added to the fast path) and directly serves the Phase 1 exit criterion on cognitive-loop believability. The `world_events`/`observable_events`/schema work (Problem B) is also **Phase 1**, folded directly into 1.1.1 since it hasn't merged. The scripted-timeline and citizen-triggered producers are naturally **Phase 2** (Phase 1's single hardcoded scenario and core-only tool catalog don't need either to hit their own exit criteria, though both are cheap enough to seed minimally in Phase 1 as a stretch item). The threshold-crossing producer's one concrete case depends on the ledger and waits for **Phase 3** (§7).

## Addendum — Salience Predefined at Creation, Not Looked Up at Read Time

Post-review refinement: salience/urgency is **predefined by the producer at the moment it creates an event row**, not inferred later by Observation via a generic event-type lookup. Concretely: `ToolDefinition` (§5.2) gains a `default_salience` field consulted by Skill Execution/Talking when logging a `simulation_events` row; each `scripted_events` entry in a scenario package carries its own explicit `salience`; the threshold-crossing producer assigns a fixed salience appropriate to its one defined case; and a citizen-triggered `world_events` row inherits its salience from the originating tool's definition. Observation's fast-path check becomes a direct comparison against the value already on the row (`event.salience >= MIN_OBSERVATION_TIER` / `URGENT_REACTION_TIER`) rather than a lookup — cheaper, and it puts the judgment where the context actually is (the producer authoring or executing the event) rather than asking Observation to infer it generically after the fact. This doesn't change anything decided above — it changes *where* salience is computed (producer, at write time), not *what* Observation does with it (fast-path threshold comparison, urgent ones bypass the Controller's normal cadence).
